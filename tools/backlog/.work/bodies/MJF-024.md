**MJF-024**

## Problem

Discovery must run daily per loop, but running it per candidate would multiply upstream API cost by the number of candidates searching for the same thing.

## Business impact

Upstream rate limits and costs are the binding constraint on how many candidates the platform can serve.

## Technical impact

Resolve distinct search specs across all active loops, distribute runs across the day, hold a distributed lock per spec and source, and persist resumable cursors on discovery_runs.

## Proposed solution

Implement the scheduler binary with Redis leader election. Plan by spec hash, not by candidate, so N candidates searching identically cost one upstream query. Spread runs to smooth load and respect upstream limits.

## Acceptance criteria

- [ ] Two loops with identical specs produce one upstream query
- [ ] Only one scheduler instance plans at a time, via a Redis leader lock
- [ ] A worker crash resumes a run from its cursor rather than restarting it
- [ ] Runs are distributed across the day rather than bursting
- [ ] Every run records start, end, counts and errors, visible in the admin UI

## Testing requirements

Integration test with two identical loops asserting a single fetch. Crash-and-resume test. Leader-election test with two schedulers.
