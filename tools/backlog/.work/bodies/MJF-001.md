**MJF-001**

## Problem

There is no object-storage layer. CV uploads cannot be accepted at all, and the upload endpoint is the single highest-risk input in the product: it accepts arbitrary binary documents from the internet.

## Business impact

No CV upload means no product. Every downstream feature depends on it.

## Technical impact

Needs an S3-compatible client, streaming size enforcement, content-type verification by magic bytes rather than extension or client-supplied MIME, per-tenant opaque key namespacing, presigned download URLs, and an orphaned-object reaper for uploads never committed.

## Proposed solution

Implement internal/platform/storage over minio-go. Verify type by sniffing the first bytes, enforce the size cap during the stream so an oversized file is rejected mid-transfer rather than after being buffered, namespace keys under tenants/{user_id}/{uuid}, and issue short-TTL presigned URLs so the application is never on the bytes path. Add a ClamAV client and quarantine on a positive result.

## Acceptance criteria

- [ ] Only PDF and DOCX are accepted, verified by magic bytes; a .pdf-named ZIP is rejected
- [ ] A file over STORAGE_MAX_CV_BYTES is rejected during transfer, not after
- [ ] Keys are opaque UUIDs under a per-tenant prefix; no filename is used in the key
- [ ] Download URLs are presigned with a TTL of 5 minutes or less
- [ ] An AV-positive file is quarantined, the candidate is notified, and the object is deleted after retention
- [ ] The bucket is created on first use so no broad storage credentials are needed in the app

## Testing requirements

Unit tests for magic-byte detection across valid PDF/DOCX and hostile inputs (polyglot, ZIP renamed, empty, truncated). Integration test against MinIO covering upload, presign, download and delete.
