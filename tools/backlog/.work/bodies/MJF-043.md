**MJF-043**

## Problem

Submission is where an error becomes irreversible. A duplicate application cannot be recalled.

## Business impact

Applying twice to one job damages the candidate's standing with that employer.

## Technical impact

Submitters per method, an idempotency key persisted before dispatch, bounded retries for transient failures, and a first-class outcome_unknown state when a request was sent but the response was lost.

## Proposed solution

Implement the Submitter contract with the key written before dispatch and completed after. On redelivery with a key in_flight, report outcome_unknown and dead-letter rather than repeating a possibly-successful send. Never auto-retry an unknown outcome.

## Acceptance criteria

- [ ] Submit is safe to call twice with the same idempotency key
- [ ] A lost response produces outcome_unknown, never a guess or a silent retry
- [ ] Transient failures retry with backoff up to a cap, then fail with a reason
- [ ] Permanent failures are terminal with a reason
- [ ] Per-destination-domain rate limits are enforced
- [ ] The pre-send gate re-checks authorisation, cap, pause flag, suppression and cooldown

## Testing requirements

Idempotency tests per method. A simulated lost-response test asserting outcome_unknown and no retry. A concurrency test with two workers on one application asserting a single submission.
